# Corki prompt catalog

Prompt text is organized by when it becomes visible to the model.  The files
are modeled on the corresponding Codex CLI prompt layers, with Corki-specific
names. Configured permission instructions are generated by the pinned native
renderer; the fixed legacy Disabled/Never text is bundled under `permissions/`.

## Normal coding turn

For a first user turn in Default mode, the harness supplies these layers:

| Order | Template | Model role | Condition |
| --- | --- | --- | --- |
| 1 | Configured/session/model base, otherwise `agent/base.md` | Responses `instructions`; Chat Completions first `system` message | The selected base is retained through the turn and compaction |
| 2 | `permissions/fragment.md` | `developer` | Full policy initially; changed policy or newly approved prefixes later |
| 3 | `modes/default.md` | `developer` | Default collaboration mode |
| 4 | `context/agents.md` | `user` context | Applicable `AGENTS.md` exists |
| 5 | `context/environment_fragment.md` with typed environment state | `user` context | Initial context or a changed environment/date/timezone/authority |
| 6 | none | `user` | The user's question is sent unchanged |

Tool descriptions are not Markdown prompts.  They are sent separately as tool
JSON schemas.  Tool results and previous messages are structured conversation
items rather than prompt templates.

Roles in the table are harness roles. The generic Chat Completions adapter maps
developer context to `system`; Responses retains `developer`. Project instructions
and environment information remain `user` in both protocols, including after
compaction and cold resume. Initial context groups developer fragments before
user fragments; persisted history is not globally reordered during updates.

AGENTS.md is a session-owned snapshot, not reread on every tool step. Environment
selection or trust changes invalidate the project snapshot; cold startup reloads
it. Changed or removed project instructions produce explicit replacement/removal
notices. Permission changes restate the policy, while additions to approved
command prefixes can produce only an incremental notice. Disabling environment
or permission injection clears its baseline without pretending to revoke old text.

### Base instruction selection

An explicit `base_instructions` setting (including an empty string) takes
precedence over the persisted session base. For a new session without an
override, the local model catalog's instructions/template are used when
provided; otherwise `agent/base.md` supplies the generic fallback. Resuming an
existing session does not silently replace its stored base with a newer bundled
template. Model changes can add developer-context instructions without rewriting
the original session prefix.

The generic fallback follows Codex's `models-manager/prompt.md`, with Corki
identity, actual `apply_patch` parameters, conditional tool availability,
project-context roles, and terminal capabilities adapted to this runtime.
Model-specific official-service templates are not combined into this fallback.
Ordinary providers use the standard request fields above, not a proprietary
Responses Lite prefix. See `tests/integration/test_base_prompt_wire.py` for
captured requests across source selection, compaction, and cold resume.

## Other templates

- `modes/plan.md` replaces `modes/default.md` only in Plan mode.
- `tasks/compact.md` is used only when conversation history is summarized.

Templates use strict `#{variable_name}` placeholders.  Keep selection,
conditionals, and composition in Python rather than adding logic to Markdown.

## Extension templates

`extensions/skills/` contains the implemented metadata catalog, usage rules,
selected-skill wrapper, and catalog state notices. The catalog is developer
context; a selected skill's body is an independent user message tied to the
admitted input and source path. Ordinary local skill bodies are read completely
up to Corki's 128 KiB resource limit. The separate `skill_read` tool's output can
still be truncated by the model-output budget; its description explains how to
continue using bounded ordinary file reads rather than nonexistent pagination.

`extensions/plugins/`, `extensions/mcp/`, and `realtime/` also contain implemented
templates. Selection and lifecycle remain in their owning Python contributors;
the realtime templates describe live text steering, not a voice intermediary.
Not every model-facing instruction lives in this directory: tool schemas,
errors, and dynamically constructed collaboration instructions require auditing
their builders and final model requests as well.

## Memory templates

`memory/read_path.md` contributes session-level developer context only when
memory use is enabled and `memory_summary.md` is readable and nonempty. The
summary alone has a token budget; routing, verification, citation, and explicit
user-request-only update rules are not trimmed by that budget. Like Codex, the
curated index is embedded in this policy fragment. It is frozen for the current
context window and refreshed when a new initial context is built, not on every
tool step. Disabling memory use removes tool availability without rewriting old
history; a later window has no memory fragment while disabled.

Detailed memory and memory skills are read as ordinary tool results, never
converted into new system/developer messages. Memory skills use exact paths
under the memory root, not the ordinary `skill_read` name catalog. Source
conversations are bounded read-only queries against the supplied SQLite archive,
not Codex JSONL files. The `oai-mem-citation` marker is a local parsing format,
not a connection to an official service; raw assistant output is preserved for
model replay while the visible answer and structured citation are stored apart.

`memory/stage_one_system.md` and its input wrapper describe extraction from a
historical transcript, not execution of its instructions. Consolidation uses
`memory/consolidation.md` as the worker's task, with runtime-specific shared-root
or private-workspace instructions. Source bodies remain file-backed and are read
through tools. `memory/ad_hoc_instructions.md` matches Codex's rules: notes can
request adding/updating/forgetting remembered information, but are not commands
to execute; never delete the notes themselves. Startup seeds this resource only
when absent and preserves existing user edits. These are model instructions,
not proof that an arbitrary model will obey the explicit-request boundary.

Captured-request evidence lives in `test_memory_read_policy.py`,
`test_memory_generation_prompt.py`, and `test_memory_consolidation_prompt.py`
under `tests/integration/`, alongside citation/replay and lifecycle regressions.
Full policies can exceed very small configured windows; the runtime reports that
limit rather than silently enlarging the window or dropping the policy.

## Planning and collaboration boundary

Plan/Default mode is host-selected developer context. `None` selects the local
preset, custom text replaces it verbatim, and an empty string emits an empty
wrapper to clear prior mode instructions. Updates append once to history; a new
window contains the current mode and cold resume does not duplicate it. User
text containing the wrapper does not change the host-selected mode. Corki owns
the local presets; it does not implement Codex's model-catalog collaboration
message variants or multi-agent mode/role catalogs.

The default registry has no general-purpose `spawn_agent`/mailbox collaboration
tools. Typed child-session provenance and lifecycle hooks are not a promise of
model-driven delegation. Do not inject Codex multi-agent role/mode instructions
without the corresponding capability. `update_plan` is disallowed in Plan mode;
`request_user_input` is root-only and also respects its configured mode/host
availability. See the collaboration-mode, request-user-input, and plan-contract
integration tests, plus `test_collaboration_prompt_wire.py` for captured HTTP
mode updates, compaction, and cold resume.

## Code Mode tool instructions

`tools/code_mode_exec.md` and `tools/code_mode_wait.md` are tool descriptions,
not new developer messages. They retain Codex's helper-by-helper usage and cell
lifecycle guidance with QuickJS worker, actual result shapes, transient store,
and JSON-schema documentation adapted to Corki. The exec builder appends direct
nested definitions; deferred definitions remain discoverable through `ALL_TOOLS`.
MCP catalog guidance distinguishes ordinary direct-call discovery from Code Mode
nested discovery so it does not require a redundant `tool_search` call for tools
already present on the cell's `tools` object. Availability/exclusion policy still
controls the actual tools in each cell.

## Context windows and local recovery

Initial context grouping follows Codex's named placement rules: model-switch
instructions lead the developer bundle, including before extension fragments;
personality instructions join that bundle. Managed host policy is a separate
developer message after contextual user fragments (project/environment) and
before the incoming user input. Incremental model/personality updates remain
standalone. Recorded groups are immutable; cold replay does not regroup history.

Local compaction preserves base instructions and sends the configured compact
task as the final user message without tools. Its summary remains user context,
not a new developer policy. Manual compaction rebuilds context on the next turn;
mid-turn compaction retains the current input and positions the summary last.
SQLite keeps original records while the model receives a bounded projection.

The optional local history/notes hint contains only fixed host guidance. Note
paths and bodies are model/tool-controlled data and are obtained through tools,
never interpolated into that developer hint. This local implementation does not
use Codex account endpoints, encrypted remote history, or cross-agent storage.
See `test_base_prompt_wire.py`, `test_context_message_groups.py` and
`test_local_history_notes.py` for request-level ordering and trust-boundary tests.
