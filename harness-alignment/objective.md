/goal

  以 /Users/corki/IdeaProjects/ad/codex 的本地源码为参考，系统审计并完善 /
  Users/corki/PycharmProjects/corki，使 Corki 的 Agent Harness 核心行为尽可能
  与 Codex 一致。

  本任务是“源码审计 → 差异确认 → 实现修复 → 行为验证”的完整工程任务，不止输出
  分析报告。不要继续修改 teach.md。

  一、建立明确的对齐基准

  1. 首先读取两项目的适用开发说明，记录 Codex 当前 commit、相关未提交变更和
  Corki 的当前状态，保留用户已有改动。
  2. 每个模块先完整追踪 Codex 的真实调用链，再追踪 Corki 的对应链路，不能先假
  定 Corki 已实现。
  3. 区分 Codex 的默认路径、配置控制路径、模型/provider 能力控制路径及实验功
  能。说明 Corki 对齐的是哪条路径、在什么条件下生效。
  4. 对齐重点是可观察行为、状态转换、数据契约与故障语义；Python/LangGraph 不
  必逐行复刻 Rust。
  5. 不允许用“语言不同”“教学简化”“工具数量少”等理由，将核心缺失直接判定为可接
  受。
  6. provider 不支持 Codex 原生协议时，优先实现行为等价的兼容方案，并明确其与
  原生路径的差异，不能只留下枚举、空接口或 TODO。

  二、逐项审计并修复以下范围

  A. 主循环与 Runtime
  - Thread、Turn、Model Step 的边界及状态生命周期。
  - prepare → model → evaluate → tools → prepare 的真实循环。
  - 模型同时返回正文、reasoning、工具调用时如何处理。
  - 继续执行、完成、失败、取消、预算耗尽的判断。
  - 多工具调度、并行/独占、结果排序、执行期间的新输入。
  - 流式事件、backpressure、资源所有权及关闭顺序。
  - checkpoint、业务历史、模型结果与工具副作用之间的恢复关系。
  - 中断恢复是否重复用户输入、模型采样或工具执行。

  B. Tool Use：发现、召回、选择与执行
  - 内置工具、MCP、动态工具和扩展工具怎样注册。
  - Direct、Deferred、ModelOnly、CodeModeOnly、Hidden 等曝光策略。
  - tool_search 的启用条件、搜索元数据、索引、排序、Top-K、缓存与失效。
  - 模型如何发起搜索，检索结果如何成为后续可调用工具。
  - 原生 tool_search_output 与兼容 function-calling 路径。
  - 已发现工具的生命周期、上下文占用与恢复语义。
  - 模型选择工具和程序筛选候选之间的职责边界。
  - 名称/namespace 映射、schema 校验、调用身份、工具结果规范化。
  - 未曝光工具、未知工具、畸形参数、工具失效、超时和结果超限的处理。
  - Code Mode 与工具发现相关的路径及其适用条件。

  不能再把“全量直接曝光后由模型选择”描述为已经对齐 Codex 的按需检索。

  C. Context：构建、管理、压缩与召回
  - instructions、用户输入、项目规则、环境、工具定义和扩展信息的来源、角色及
  顺序。
  - 每 Step 更新、稳定 key、增量快照、删除/tombstone 与历史视图。
  - 完整请求的 token 估算、输出预留、工具 schema 和附件成本。
  - 自动/手动压缩的触发、时机、输入选择、摘要生成与失败处理。
  - 当前用户输入、关键约束、reasoning 和 tool call/result 的保留规则。
  - 压缩结果怎样替代模型可见历史，以及原始记录如何保存。
  - 连续历史召回、历史检索、长期记忆召回的区别及实际实现。
  - 恢复、取消或工具执行途中发生压缩时的一致性。
  - provider 特有的上下文和压缩路径，不得把不适用路径混为一谈。

  D. Memory：短期、工作与长期记忆
  - 同 Thread 跨 Turn 历史、模型可见窗口与工作状态的边界。
  - 长期记忆的来源筛选、触发条件、提取、合并、存储和发布。
  - claim、lease、owner、source version、watermark、去重及失效。
  - summary 注入、按需检索、详细读取、来源引用与使用反馈。
  - 显式记住、更新、遗忘，以及外部内容污染控制。
  - 后台任务与主循环的关系、失败隔离、取消和关闭。
  - 遵循 Codex 实际实现，不预设长期记忆必须使用向量数据库。

  E. 错误处理与降级
  - 明确区分可作为 Observation 返回模型的错误、可重试错误、Turn 致命错误及取
  消控制流。
  - 覆盖未知工具、非法 JSON/schema、handler 异常、MCP 断连、工具超时、超长/非
  法结果。
  - 覆盖模型 HTTP 错误、流截断、缺失终态、部分输出后的失败与重试限制。
  - 覆盖压缩失败、记忆失败、扩展初始化失败和部分注册回滚。
  - 重试必须结合幂等性与副作用风险，不能自动重放结果未知的操作。
  - 不得把失败或半截输出标成成功，也不得吞掉取消。
  - 核对每个逻辑 Turn 的终态和所有资源清理路径。

  三、先建立有证据的差异清单

  在修改前先产出并保存一份核心对齐审计文档，至少包括：

  - 行为项及触发场景。
  - Codex 的源码路径、关键函数、调用链及相关测试。
  - Corki 的对应源码和当前行为。
  - 状态：一致、部分一致、缺失、行为不一致、不适用。
  - 差异造成的实际影响和优先级。
  - 修复方案及可验证的验收条件。

  “没有发现问题”不能作为一致的证据。
  “不适用”必须给出具体的配置、能力或产品边界依据。
  审计文档随实现持续更新，不能停留在初始判断。

  四、按依赖顺序完成修复

  1. 审计形成足够明确的结论后，分批修复协议、状态、工具发现、上下文、记忆和故
  障处理。
  2. 尽量复用现有架构，避免无关重写；同时不能为了保留旧结构而牺牲核心行为。
  3. 每批修复都要接入真实主循环，不能只新增脱离 Runtime 的示例模块。
  4. 新增持久化字段时考虑已有数据库和 checkpoint 的兼容性。
  5. 若核心问题涉及安全执行或审批边界，必须说明；不要顺带扩张为完整重建 Codex
  UI、部署系统或所有外围功能。

  五、以行为证据验收

  为重要差异编写能在修复前暴露问题、修复后通过的测试，并尽可能把 Codex 的相关
  测试场景映射到 Corki。

  至少覆盖：
  - 按需搜索 → 工具定义可用 → 模型调用 → Observation 回灌。
  - 已加载工具的跨 Step 行为与恢复。
  - 多 Step、多工具及同 Thread 跨 Turn。
  - 小上下文窗口下压缩、当前输入保留、工具关系完整。
  - 长期记忆提取/合并/召回及失败隔离。
  - 模型提交、工具 claim、工具完成等关键故障窗口。
  - 错误降级、重试边界、取消、backpressure 和资源清理。

  使用 ScriptedModel、mock provider/MCP 与故障注入保证核心测试离线、确定性。
  明确：预设 ToolCall 的测试只能证明 Harness 链路，不能证明真实模型的工具选择
  质量。真实模型验证应独立记录，不能冒充已执行。

  最后运行与修改范围匹配的测试及项目要求的静态检查，并完成至少一个组合多个核
  心模块的端到端场景。不能只依赖原有测试全绿来证明新能力已经实现。

  六、完成条件

  只有在范围内各项差异均已修复并验证，或有明确依据判定不适用，且没有未说明的
  重要缺口时，才能宣称核心对齐完成。

  最终交付：
  - 更新后的核心对齐审计文档。
  - 实际接入 Corki 的实现及测试。
  - 已关闭差异与验证证据。
  - 仍存在的差异、限制、未执行验证及原因。

  不能用文档描述代替代码实现，不能用接口预留代替功能，不能用局部测试代替全链
  路证据，也不能因为工作量大或已有部分进展就提前宣布完成。
